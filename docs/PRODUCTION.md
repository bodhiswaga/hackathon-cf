# Эксплуатация CampusFlow

## Локальная проверка production

Из корня проекта скопируйте `.env.production.example` в `.env.production`. Задайте независимые случайные POSTGRES_PASSWORD, JWT_SECRET и REGISTRATION_INVITE_CODE (рекомендуется по 32 случайных байта в hex). Файл исключён из Git и Docker context. Пароль БД в URL должен быть hex либо URL-encoded.

```powershell
docker compose --env-file .env.production -f compose.production.yaml -p campusflow-prod-check up --build -d
docker compose --env-file .env.production -f compose.production.yaml -p campusflow-prod-check exec web python -m backend.cli create-admin --login operator --name "Администратор кампуса"
```

CLI запрашивает пароль скрыто, минимум 12 символов. Повторное создание существующего логина запрещено. Сайт http://127.0.0.1:8081 доступен только с этого компьютера; демо — http://127.0.0.1:8080. Production volume отдельный, демонстрационные записи не загружаются. Для проверки в рабочей папке уже созданы `.env.production` и оператор `operator`; его первоначальный случайный пароль находится в локальном BOOTSTRAP_ADMIN_PASSWORD этого файла. Этот параметр не передаётся веб-приложению постоянно. Не используйте локальные секреты для публичного сервиса.

## Render

1. Опубликуйте исходники в своём Git-репозитории без `.env*`, кроме файлов `.example`, без дампов и БД. Подключите его к Render Blueprint; выберите `render.production.yaml` как Blueprint Path. `render.yaml` предназначен только для демонстрации.
2. Blueprint содержит платные web `0.5c-512mb` и PostgreSQL `0.5c-1g`. Перед созданием проверьте оценку стоимости в Render. Платные сервисы в ходе локальной разработки не создавались.
3. ALLOWED_HOSTS задайте точным hostname назначенного Render-сервиса, без https и пути, плюс свой домен через запятую при его наличии. Не используйте `*`. JWT_SECRET и код приглашения генерируются Render; APP_ENV=production и SEED_DATA=false обязательны.
4. Pre-deploy выполняет `python -m backend.migrate`. Приложение проверяет версию схемы при старте и отказывается работать с неподходящей. Внешние подключения к БД отключены `ipAllowList: []`; приложение использует внутренний URL.
5. В Render Shell выполните `python -m backend.cli create-admin --login operator --name "Администратор кампуса"` и введите уникальный пароль. Войдите через HTTPS, добавьте реальные аудитории. Передавайте код приглашения только участникам кампуса; его смена закрывает старые приглашения, сохраняя существующие аккаунты.
6. Проверьте `/api/health` (200), отсутствие демонстрационного входа, отказ `/docs` (404) и отсутствие ошибок браузера. FORWARDED_ALLOW_IPS=* допустим здесь только потому, что входящий трафик проходит через управляемый Render proxy. При самостоятельном размещении укажите адреса доверенного reverse proxy и закройте прямой доступ к uvicorn.

Актуальные имена планов и pre-deploy: [Render compute plans](https://render.com/docs/compute-plans), [Blueprint reference](https://render.com/docs/blueprint-spec). План не гарантирует заданную нагрузку: перед массовым запуском измерьте свою ожидаемую конкурентность.

## cron-job.org и мониторинг

Создайте HTTPS GET `https://<host>/api/health` каждые 10 минут, включите уведомления о сбоях в аккаунте cron-job.org и выполните Test run. Endpoint проверяет соединение с БД; `/api/live` проверяет только процесс. Сервису мониторинга не нужны пароли пользователей.

Альтернатива: задайте CAMPUS_URL и CRONJOB_API_KEY в окружении, выполните `python scripts/setup_cron.py`. Запускайте один раз: скрипт создаёт новый job при каждом вызове. API-ключ не храните в Git. На платном Render ping служит мониторингом; на бесплатном демо не является гарантией непрерывной доступности. Настройку публичного задания можно проверить только после выкладки.

## Бэкап и восстановление

Используйте автоматическое восстановление платного Render Postgres и независимые регулярные дампы. [Документация Render](https://render.com/docs/postgresql-backups). Для скриптов нужны pg_dump, pg_restore и psql версии не ниже сервера, доступные в PATH.

```powershell
# DATABASE_URL берётся из защищённого окружения; не вставляйте пароль в команду.
python scripts/backup.py backups/campusflow-2026-11-15.dump
# RESTORE_DATABASE_URL — заранее созданная отдельная пустая БД.
python scripts/restore.py backups/campusflow-2026-11-15.dump
```

Дамп содержит персональные данные и хеши паролей: ограничьте доступ, храните зашифрованную копию отдельно от сервера. Рекомендуемый стартовый регламент — ежедневный дамп, хранение 14 дней, ежемесячное восстановление в изолированную БД. Скрипт не перезаписывает существующий архив; restore отклоняет непустую public-схему и выполняет восстановление одной транзакцией. В Render выполняйте дамп из доверенной внутренней среды, поскольку внешний доступ отключён.

После восстановления запустите `python -m backend.migrate`, проверьте health, количество записей, вход и бронирование на тестовой аудитории. Только затем переключайте DATABASE_URL. Не восстанавливайте поверх текущей БД.

## Обновление и действия оператора

- CI выполняет API-тесты SQLite/PostgreSQL, TypeScript/Vite build и Docker build. После размещения в GitHub убедитесь, что workflow завершился успешно; локальный прогон не означает выполненный GitHub Actions.
- Перед изменением схемы создайте бэкап. Миграции выполняются однократно под PostgreSQL advisory lock. Первая миграция сохраняет данные старой версии; переход на серверные сессии завершает старые входы.
- Откат приложения допустим только к версии, совместимой с текущей схемой. Автоматический downgrade исходной схемы запрещён. При несовместимости восстанавливайте бэкап в отдельную БД и переключайте сервис.
- Забытый пароль: `python -m backend.cli reset-password --login <login>`. Все сессии пользователя отзываются. Сначала проверьте личность заявителя по процедуре кампуса.
- Ежедневная служебная очистка: `python -m backend.cli cleanup`. Удаляет истёкшие сессии и старые лимитирующие счётчики, не брони и не журнал действий. Запускайте из доверенного планировщика с DATABASE_URL, не через публичный HTTP endpoint.
- Аудит: администратор получает `/api/admin/audit?limit=100&before=<id>`. Записываются изменения профиля, паролей, сессий, комнат и броней; пароли и токены не записываются. Доступ к журналу — только admin.
- Логи содержат request ID, метод, путь, статус и длительность. При ошибке пользователь получает безопасное сообщение. Не включайте SQL echo и логирование HTTP body в production.
- В случае утечки JWT_SECRET замените его: старые токены перестанут приниматься. Смените раскрытые пароли и код приглашения отдельно.

## Приёмка после выкладки

`scripts/check_deployment.py` использует CAMPUS_URL, ADMIN_LOGIN, ADMIN_PASSWORD и REGISTRATION_INVITE_CODE из окружения. Проверяет создание, конфликт параллельных броней, отмену, архивирование и отзыв сессии. Оставляет технического студента, архивную аудиторию и отменённую бронь для аудита — запускайте осознанно. При REGISTRATION_MODE=closed используйте тестовое окружение с приглашениями.

Публичный запуск завершён после успешного HTTPS-входа, проверки прав, успешного health из cron-job.org, настройки получателя аварийных уведомлений и проверки доступного бэкапа. Вход в аккаунт Render и создание внешнего cron job требуют участия владельца; локальная проверка этих действий не заменяет.

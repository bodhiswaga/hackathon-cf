# Эксплуатация CampusFlow

## Локальная проверка production

Из корня проекта скопируйте `.env.production.example` в `.env.production`. Задайте независимые случайные POSTGRES_PASSWORD, JWT_SECRET и REGISTRATION_INVITE_CODE (рекомендуется по 32 случайных байта в hex). Файл исключён из Git и Docker context. Пароль БД в URL должен быть hex либо URL-encoded.

```powershell
docker compose --env-file .env.production -f compose.production.yaml -p campusflow-prod-check up --build -d
docker compose --env-file .env.production -f compose.production.yaml -p campusflow-prod-check exec web python -m backend.cli create-admin --login operator --name "Администратор кампуса"
```

CLI запрашивает пароль скрыто, минимум 12 символов. Повторное создание существующего логина запрещено. Сайт http://127.0.0.1:8081 доступен только с этого компьютера; демо — http://127.0.0.1:8080. Production volume отдельный, демонстрационные записи не загружаются. Используйте независимые секреты для локального и публичного сервисов.

## Render Free: демонстрация и prod-ready приложение

Обзор двух вариантов развёртывания находится в [README](../README.md#render-и-cron-joborg). Порядок настройки приведён ниже.

- `render.yaml`: один бесплатный web, временная SQLite с учебными данными. После перезапуска изменения могут исчезнуть; seed создаётся заново.
- `render.production.yaml`: бесплатный web и единственная бесплатная PostgreSQL workspace, APP_ENV=production, SEED_DATA=false, приглашения и закрытый Swagger.
- В Render выберите **New → Blueprint**, подключите репозиторий `bodhiswaga/hackathon-cf` и ветку `main`. Создайте два независимых Blueprint, выбирая соответствующий Blueprint Path из списка выше. Проверьте планы **Free** и нажмите **Deploy Blueprint**. Не управляйте одним ресурсом из двух Blueprint.
- Free не поддерживает pre-deploy и Shell. `python -m backend.launch` до открытия HTTP-порта выполняет миграции под advisory lock, затем первичное создание администратора. Render hostname добавляется в ALLOWED_HOSTS автоматически. При своём домене добавьте точное имя в ALLOWED_HOSTS.
- При первом деплое задайте BOOTSTRAP_ADMIN_PASSWORD (12+ символов); логин по умолчанию operator. После успешного входа удалите переменную из Render Environment и передеплойте. Существующий пароль при перезапуске не меняется; существующему студенту bootstrap не повышает роль.
- JWT_SECRET и REGISTRATION_INVITE_CODE генерируются отдельно от демо. Код выдаётся участникам кампуса, секрет JWT — только серверу.
- Внешний доступ к PostgreSQL отключён (`ipAllowList: []`). Не открывайте БД всем адресам ради администрирования. Для CLI с вашего компьютера можно временно разрешить только свой публичный IPv4/32, использовать External Database URL с sslmode=require через защищённое окружение и после операции удалить правило.

## cron-job.org, лимиты и мониторинг

Создайте по заданию HTTPS GET `/api/health` для каждого сайта, каждую минуту в часы работы кампуса, без авторизации. Включите email-уведомления, выполните Test run → 200 и проверьте History. `/api/health` проверяет БД, `/api/live` — только процесс.

750 instance-hours в месяц — общий лимит workspace. Два сайта 24/7 потребуют 1440 часов за 30 дней. Для хакатона включайте оба задания на время показа. Для работы в течение месяца используйте оба задания с timezone Asia/Yekaterinburg, часами 09–19 и всеми минутами: оставляйте запас общего лимита на задержку засыпания и пользовательские обращения. Пользовательский трафик вне расписания увеличит расход. Контролируйте Billing → Monthly Included Usage. Cron уменьшает вероятность сна внутри окна, но не гарантирует непрерывную доступность и не продлевает БД.

Free PostgreSQL: одна на workspace, срок 30 дней, без managed backups. До истечения сделайте дамп и перенесите данные. Бесплатный хостинг позволяет показать production-конфигурацию приложения, но не предоставляет гарантий инфраструктуры для постоянной эксплуатации. [Ограничения Render](https://render.com/docs/free).

Альтернатива ручному созданию job: CAMPUS_URL и CRONJOB_API_KEY в окружении, `python scripts/setup_cron.py`. Скрипт создаёт новое круглосуточное задание при каждом вызове. Для двух сайтов запускайте по одному разу с разными CAMPUS_URL; затем задайте дневное расписание и интервал каждую минуту в консоли (скрипт по умолчанию задаёт 10 минут). Ключ в Git не храните.

## Бэкап и восстановление

На бесплатном Render автоматических бэкапов нет: делайте независимые регулярные дампы. При переходе на платную БД можно дополнительно использовать managed recovery: [документация Render](https://render.com/docs/postgresql-backups). Для скриптов нужны pg_dump, pg_restore и psql версии не ниже сервера, доступные в PATH.

```powershell
# DATABASE_URL берётся из защищённого окружения; не вставляйте пароль в команду.
python scripts/backup.py backups/campusflow-2026-11-15.dump
# RESTORE_DATABASE_URL — заранее созданная отдельная пустая БД.
python scripts/restore.py backups/campusflow-2026-11-15.dump
```

Дамп содержит персональные данные и хеши паролей: ограничьте доступ, храните зашифрованную копию отдельно от сервера. Рекомендуемый стартовый регламент — ежедневный дамп, хранение 14 дней, ежемесячное восстановление в изолированную БД. Скрипт не перезаписывает существующий архив; restore отклоняет непустую public-схему и выполняет восстановление одной транзакцией. Для дампа с локального компьютера временно разрешите только свой IP в настройках БД, используйте External Database URL с sslmode=require, затем закройте правило. Никогда не публикуйте этот URL.

После восстановления запустите `python -m backend.migrate`, проверьте health, количество записей, вход и бронирование на тестовой аудитории. Только затем переключайте DATABASE_URL. Не восстанавливайте поверх текущей БД.

## Обновление и действия оператора

- CI выполняет API-тесты SQLite/PostgreSQL, TypeScript/Vite build и Docker build. После размещения в GitHub убедитесь, что workflow завершился успешно; локальный прогон не означает выполненный GitHub Actions.
- Перед изменением схемы создайте бэкап. Миграции выполняются однократно под PostgreSQL advisory lock. Первая миграция сохраняет данные старой версии; переход на серверные сессии завершает старые входы.
- Откат приложения допустим только к версии, совместимой с текущей схемой. Автоматический downgrade исходной схемы запрещён. При несовместимости восстанавливайте бэкап в отдельную БД и переключайте сервис.
- Забытый пароль: `python -m backend.cli reset-password --login <login>`. Все сессии пользователя отзываются. Сначала проверьте личность заявителя по процедуре кампуса.
- Ежедневная служебная очистка: `python -m backend.cli cleanup`. Удаляет истёкшие сессии и старые лимитирующие счётчики, не брони и не журнал действий. Запускайте из доверенного планировщика с DATABASE_URL, не через публичный HTTP endpoint.
- Аудит: администратор получает `/api/admin/audit?limit=100&before=<id>`. Записываются изменения профиля, паролей, сессий, комнат и броней; пароли и токены не записываются. Доступ к журналу — только admin.
- Логи содержат request ID, метод, путь, статус и длительность. При ошибке пользователь получает безопасное сообщение. Не включайте SQL echo и логирование HTTP body в production.
- В случае утечки JWT_SECRET замените его: старые токены перестанут приниматься. Смените раскрытые пароли и код приглашения отдельно.

## Приёмка после выкладки

`scripts/check_deployment.py` использует CAMPUS_URL, ADMIN_LOGIN, ADMIN_PASSWORD и REGISTRATION_INVITE_CODE из окружения. Проверяет создание, конфликт параллельных броней, отмену, архивирование и отзыв сессии. Оставляет технического студента, архивную аудиторию и отменённую бронь для аудита — запускайте осознанно. При REGISTRATION_MODE=closed используйте тестовое окружение с приглашениями.

Публичный запуск завершён после успешного HTTPS-входа, проверки прав, успешного health из cron-job.org, настройки получателя аварийных уведомлений и проверки доступного бэкапа. Вход в аккаунт Render и создание внешнего cron job требуют участия владельца; локальная проверка этих действий не заменяет.
